Work through this in strict phases. Do not proceed to a new phase until the current one is complete. After each phase, output a written summary of what was changed, what was skipped, and what requires human review.

## PHASE 2 — SUPABASE VALIDATION

Work through every Supabase interaction identified in Phase 1.

### Edge function testing
For each edge function:
- Identify its trigger (HTTP endpoint, database webhook, scheduled cron)
- Test it with representative inputs covering happy path, edge cases, and expected error states
- Verify it returns the correct status codes and response shapes
- Verify error handling does not leak sensitive information
- Check for missing or misconfigured CORS headers
- Check for hardcoded secrets or environment variable misuse
- Flag any function that is never called by the app (dead function)

### Database call validation
For each Supabase client query (.select, .insert, .update, .delete, .rpc):
- Confirm the query targets the correct table and columns
- Confirm filters (.eq, .match, .in) are applied before returning data, not after
- Confirm RLS (Row Level Security) policies are in place for every table touched by the app
- Confirm no query fetches unbounded data without a .limit()
- Confirm auth context is passed correctly (using supabase.auth.getSession() or equivalent)

### 3NF compliance audit
For every table in the schema:
- Confirm each table has a single-column primary key (or a well-justified composite key)
- Confirm no column is functionally dependent on a non-key column (no transitive dependencies)
- Confirm no repeating groups or multi-value columns
- Confirm foreign key relationships are explicit and enforced
- Flag any table that stores denormalized data for performance reasons — note the tradeoff explicitly

Output a pass/fail/warning for every edge function and every table. List all changes made and any recommended refactors that require human review.

## PHASE 5 — SEO, GEO, AND AIO IMPLEMENTATION

Apply only to the web app. Mobile apps are not in scope for this phase.

### SEO (Search Engine Optimization)
For every public-facing web page:
- Add a unique, keyword-relevant <title> tag (50–60 characters)
- Add a unique <meta name="description"> (120–160 characters)
- Add canonical <link rel="canonical"> tags
- Ensure heading hierarchy is correct (one H1 per page, logical H2/H3 nesting)
- Add alt text to every image that is not purely decorative
- Confirm all internal links use descriptive anchor text (not "click here")
- Add Open Graph tags (og:title, og:description, og:image, og:url) to every shareable page
- Add Twitter Card meta tags
- Generate or update sitemap.xml to include all public routes
- Generate or update robots.txt

### GEO (Generative Engine Optimization)
GEO makes content legible and citable by AI-powered search engines (Perplexity, ChatGPT search, Google SGE, Bing Copilot). For every content-heavy page:
- Use clear, declarative sentences that state facts directly (avoid marketing hedges like "leading" or "best-in-class")
- Add FAQ sections using <details>/<summary> or structured Q&A markup where appropriate
- Use semantic HTML5 elements (<article>, <section>, <aside>, <nav>, <main>, <header>, <footer>)
- Where the page defines a concept or process, wrap it in a concise definition block (first paragraph should be a self-contained summary)
- Avoid burying key facts in images or JavaScript-rendered content that crawlers may not index

### AIO (AI Overview Optimization)
AIO specifically targets Google's AI Overviews and similar featured answer formats:
- For any page that answers a specific question, add JSON-LD FAQ schema
- Add JSON-LD Organization schema to the root layout
- Add JSON-LD BreadcrumbList schema to nested pages
- Add JSON-LD Article or WebPage schema to blog/content pages where applicable
- For product or service pages, add JSON-LD Product or Service schema
- Use HowTo schema for any page that describes a process
- Validate all JSON-LD with Google's Rich Results Test syntax before committing
